# 技术深挖：问题、技术障碍与本次方案

## 1. 只检查 `../` 不足以约束跨平台路径

技术问题包括反斜杠/盘符、NTFS 流、保留设备名、尾点/空格和大小写别名。仅靠“拼上目录后看字符串前缀”还会混淆共同前缀；静默清洗名称则改变了语义、可能使两个输入归并。

本次方案不是兼容所有文件名：对 **原始 ZipInfo 名称**实施保守 ASCII 相对路径策略，不做 URL 解码/规范化修复；拒绝 `orig_filename != filename`，防止忽略 NUL 截断或平台分隔符转换。分段验证后，维护大小写不敏感的全路径与每一个目录前缀命名空间。

例子：`Docs/a.txt` 和 `docs/b.txt` 的最终文件名不相同，但在不同平台上可能合并或分裂目录，因此前缀拼写差异也拒绝。`a.md` 与 `a.md/b.txt` 则是文件/目录冲突。显式 `docs/` 可与隐式同名目录共存，但重复显式成员不行。

证据：路径表分别注册独立 unittest 项目；另测重复/大小写/前缀/顺序两向冲突、NUL 原名。所有拒绝都断言未创建目标容器。仍不等于兼容全部文件系统规则；后续如支持 Unicode，需要另设正规化、别名与迁移约定。

这里依赖 `ZipInfo.orig_filename` 保留原名的实现行为；它不是本文引用的公开属性清单中的稳定接口承诺。当前支持范围由 Python3.11–3.13 的回归限定；升级解释器时必须重新执行 NUL/分隔符等测试，不能静默降级只用已转换名称。

## 2. ZIP 样本生成器也会“修复”坏名称

本地首轮回归发现：Windows 上 `ZipInfo` 构造时可能转换 OS 路径分隔符，导致测试中的 `safe\\file.txt` 在写入 ZIP 前已经变成 `safe/file.txt`。测试预期拒绝，实际发布；这不是靠修改预期使测试通过。

最终方案：微型**测试夹具生成器**显式保留两处名称属性，写出原始局部/中央目录名称；接收器仍然拒绝转换差异和反斜杠。Linux/Windows 因此检查相同原始样本。此赋值仅用于内存合成 ZIP，不绕过生产校验，不对危险路径做实际落盘。

首轮另有测试监视器使用错误（function 没有 mock 的调用断言），改为 `side_effect` 包装真实重命名；不把它包装成安全漏洞。修正后的实际数量及平台结果见 [验证记录](VALIDATION.md)。

## 3. 声明大小不等于观测大小

元数据计划尽早挡住明显超限，但声明来自不可信 ZIP。单看压缩率还可能误拒正常重复文本，或因分母不可靠而不能独立限制资源。

本次双层方案：

```text
validate all metadata first
for each exposed member stream:
    remaining = min(file budget, shared total budget, ratio budget)
    block = read(min(64 KiB, remaining + 1))
    if any observed budget exceeded: reject BEFORE write
    hash and write this block to private staging
read to EOF; compare observed file length with declared length
publish only after every member succeeds
```

多读的 1 字节用于识别边界超出，不写入超限数据块。跨成员共用 total budget。相等边界仍继续读一次，不能拿“正好达到声明长度”代替 EOF。库负责它所暴露流的 CRC/局部头等校验；本项目再核对实际长度。

证据：独立注入短/长的假流，验证观测 file/total/ratio 上限和写入前拒绝；64 KiB 读取上限；真实 ZIP 的 CRC 损坏、局部头名称不一致。假流测试验证的是我们的预算逻辑，不声称找到了 zipfile 绕过。

剩余问题：中央目录在 entry cap 前已经解析；解压器内部缓冲/CPU 不由这个循环硬限制。输入上限 + 流预算不是操作系统资源配额。实际部署应放独立 worker 设置时间/内存/磁盘/并发上限。

## 4. 末尾才发现错误，如何避免半包发布

问题不是简单的 try/except：第一份文档可能已落盘，第二份才出现 CRC 错误。若直接写业务目录，消费者会看到部分成功；若事后对用户目标递归清理，又可能删掉原有内容。

最终方案：

1. 全包元数据计划完成前不保留任何目标。
2. `mkdir` 不使用 exist_ok，原子独占创建**全新容器**；失败时不取得所有权、不清理它。
3. 容器下创建私有 `.pending-*`，以独占文件创建方式写入，忽略包内权限/时间戳。
4. 所有普通文件完整校验后，单次重命名 pending 目录为 `payload`；消费者只观察 payload。
5. 捕获失败时，仅清理本次成功创建的容器。清理也失败则返回 `cleanup_failed`/error，不声称无残留。

避免了直接对已有目的目录做 rename 覆盖的跨平台差异，因为目标容器由本次调用独占创建。**但并非抗恶意本地写者的无竞态算法**：同身份进程可以替换目录对象，且普通路径 API 没有持久句柄级防护。仅在私有可信工作区内成立。

证据：第二个文件坏 CRC 时首文件一并清理；预存在空目录/非空目录/文件均保持原状；在 mkdir 前注入竞争创建，其他调用者的 marker 保留；重命名失败、暂存创建失败、清理失败均有明确结果；真实重命名前观察不到 payload。

剩余问题：没有 fsync、崩溃恢复和幂等任务状态。捕获错误后的回滚不等于断电事务；强杀可留下 pending，发布后报告丢失也不能安全重复覆盖原容器。

## 5. 低泄漏证据不等于无敏感数据

拒绝时回显整段文件名/底层异常可能把客户路径写进共享日志。本次返回有限规则码、阶段、0-based 成员号、精确原名 SHA-256 和静态建议；失败不返回部分成功文件记录。

成功报告必须给出获准相对路径与内容摘要，才能重放核验。它仍然可能包含敏感业务标识，摘要也可被字典猜测。应保存在授权范围内，而非直接上传公开仓库。哈希只能绑定同一输入/输出，不证明来源真实、内容无害或链条合法。

## 6. 结构获准不是内容获准

`.txt` 内完全可以是另一份 ZIP，`.md` 也可以有脚本片段或提示词注入，CSV 可以包含电子表格公式。把所有这些归为“解压安全了”将造成下一个信任边界失守。

本次明确保持隔离接收职责，不递归解包、不渲染、不执行、不调用模型；测试专门确认二进制伪装 txt 仍可隔离获准，作为**已知漏报/非目标**证据。业务后续需要严格文本/格式解析、活性内容策略、租户授权与独立工作进程；本版本没有实现这些，不使用杀毒或生产安全网关的表述。
